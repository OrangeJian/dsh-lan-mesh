## M4：共享 Markdown 文档

实现计划中的纯状态、确定性三方合并、原子存储、签名同步、服务协调、模型工具、面板端点和文档界面。不能只完成后端后宣称 M4 完成。

- 目标场景是多人/跨系统共同澄清需求和修改澄清文档、设计文档。优先可靠版本与审计，不做实时逐字协同。
- 无冲突自动提交；过期 base 的非重叠修改自动合并，真正重叠冲突才要求人类确认。不得悄悄覆盖 head，也不能把冲突标记文本当作成功合并。
- 任何人类成员均可提出冲突解决方案；只有 Leader 或明确授予的文档维护者确认。Agent 可以提出修改，不能伪装人类确认。
- 完整永久保留提案、修订、作者/节点、base、提交说明、合并/冲突决定、审计事件及关联任务。恢复历史产生新提案/修订，不修改旧历史。
- Leader 排序，generation+seq 决定审计顺序，禁止靠墙钟排序；同检查点不同 hash 停止该文档同步并明确报错。离线提案保留，重试同 proposalId，内容变化不能复用同 ID。
- revision、audit、head、幂等记录与 outbox 同一原子事务；故障后是完整旧状态或完整新状态。不能出现 ACK 成功而修订丢失。
- 面板必须有列表/创建、阅读、编辑、diff、历史、冲突三方查看、解决提案和权限明确的确认操作；错误保留草稿。Markdown 导入/导出显式选择，导入有审计，不自动绑定磁盘双向同步或 Git。

## M5：共享项目上下文

- 实现有界 Context Pack，包含用户明确选择的文档版本、显式标记的决策/未决问题、相关消息、附件和技能引用。
- 每份文档固定 revisionId 与内容 hash；记录每次投递给哪个 Agent、实际收到哪些版本。head 后续变化不能改写已投递证据。
- 大内容截断规则确定，带授权工具读取入口；不把整个聊天历史复制进上下文，不凭模型猜测把普通语句升级为已确认决策。
- 接入 @ 和任务派发，同时保留精确成员引用、机器消歧、技能只提示可用能力和现有执行授权。附件不可达必须明确，不能冒充已读取。

## 房间生命周期

先把已确认方向写成具体状态、权限、兼容与并发方案，再按该方案实施，记录局部裁定。需满足：

- Leader 归档/恢复；归档平时隐藏，历史参与过的人类仍能在归档列表找到并查看。历史参与资格不能仅靠当前 members 推导。
- 归档建议只读并停止新派发/自动唤醒，不能借现有 retireRoom tombstone 冒充归档。保留原有执行的核对/取消能力，不能把归档当作已终止外部操作。
- 各节点保留自己的历史。退出、删除本地记录、归档是不同动作；本地删除不能同步清除其他人的副本。删除前明确范围，运行自动化不触碰用户真实历史。
- 置顶、静音是本地偏好，重启保留。静音对人类收件箱与角标生效，@ 例外要有明确设置；不隐式更改已经授权的 Agent 工作。
- 可主动移交负责人；真正无负责人时允许人类接手，离线不等于无负责人。并发接手须有唯一可解释的裁决、审计与旧权威栅栏，禁止多主静默写入。
- 房间管理者不自动成为 Team 执行 Leader、不继承其他节点执行授权，不能接管运行中任务。

## M6：自动编排的边界

在 M4/M5 可用后核对已确认的 Agent Team 架构。按既有设计推进能力描述、任务依赖 DAG、容量匹配、拆解/调度/验收及人类可审查的计划界面；默认保持 opt-in，不启用未授权执行。

依赖校验、无环、权限、容量、状态转换和验收由插件强制执行，不能只靠提示词。Worker 成功进入 review，只有合法 Leader 验收。uncertain 占容量，禁止自动重跑或另建 attempt；执行变更/房间接管不能绕过 generation 和人工对账。自动调度只能选择本机已授权范围内的成员，能力声明不授权。

当前资料若不足以确定某项 M6 重大协议/权限行为，交付具体方案、接口与测试计划，列明待决项；不要编造“已完成”，也不要因此停止已确定的其他开发。M1 的实机验收前置条件仍然有效，不能凭 localhost stub 宣称可正式自动运行。
