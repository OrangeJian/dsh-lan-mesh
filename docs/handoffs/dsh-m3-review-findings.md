## 按顺序整改

### 1. 阻塞：不能凭其他房间已有 digest 获得读取权

位置：`lib/room-attachment-ledger.mjs:58`。

接收方 commit 只检查节点级存储已有字节，缺少“该发送者、房间、准备意图已获准使用这些字节”的凭据。某摘要已在另一个房间存储时，发送者可直接准备并提交为本房间引用，继而获得读取权限。

要求：远端 commit 必须具有持久且精确限定发送者、房间、意图及不可变引用的已验证接收/授权记录。物理去重不能跳过授权证明。崩溃恢复和迁移不得把全节点 has(blobId) 当作授权；无充分证明的旧 prepared 状态须重新走合法接收或明确失败，不能清空合法已提交历史。

验收：先在另一房间存同摘要，再尝试仅 prepare+commit，必须拒绝且不得授权 GET；合法授权上传后才能提交。覆盖去重、重启、丢 ACK 和伪造 owner/metadata。

### 2. 高：目标、收件成员资格与续期新鲜度

位置：`lib/room-attachment-service.mjs:34`、`lib/room-attachment-ledger.mjs:42`。

prepare/commit 检查发送成员，却没有验证签名目标 `to` 是否为本节点、接收节点是否仍为房间成员；过期 prepare 续期不能区分捕获的旧请求原封重放与发送者发起的新请求。

要求：入站先验证目标和当前收件资格，再持久修改。续期需新鲜、完整认证的请求；同内容同 ID 的合法重试仍可恢复。保留独立能力/版本协商，不静默改旧签名语义，不以调宽时间窗口代替防重放。

验收：签名正确但 to 错误、接收方已退出、旧 prepare 重放均不产生授权；合法新请求续期后可完成 PUT/commit；重启后重放边界仍明确。

### 3. 高：已读重写和恢复不能丢附件引用

位置：`lib/service.mjs:1606`、`:2078`。

已读操作重写 inbox 时漏掉 attachments；重启恢复发现同 ID 已存在就跳过，导致附件卡消失，虽然 blob/ledger 仍在。

要求：所有 inbox 重写保留不可变引用。恢复时从可信 committed ledger 修复此前被剥离的记录，保留原 read 状态，不重复消息或唤醒。

验收：真实 MeshNode 发送附件→标记已读→关闭→新实例重开，引用、下载、已读和计数均保留；另覆盖旧磁盘记录缺引用的修复。

### 4. 高：网络等待移出事务队列，合并重试

位置：`lib/room-attachment-service.mjs:44`、`lib/service.mjs:551`。

发送期间一直持有入站 prepare/commit 也需使用的 ledger.run 队列；两节点互相同时发送会各等对方直到超时。定时 retry 扫描还可能重叠积压。

要求：仅在事务队列中完成必要原子状态修改，释放后做网络，再串行落盘结果。对同 ID 出站发送和 retry 扫描合并并发调用，避免丢更新、重复唤醒及网络洪泛；shutdown 正确终止/等待活动任务。

验收：两个真实 HTTP 节点同时互发附件能完成，不靠超时恢复；叠加手动 retry/定时扫描和丢 ACK，同一消息单次发表、pin 正确、无队列积压，关闭可完成。

### 5. 高：失败草稿不能在后台悄悄发出旧版本

位置：`lib/room-attachment-service.mjs:78`。

后台会自动重发未提交的本地准备记录；Leader 离线时界面保留可编辑草稿，用户改写/放弃后，旧版本仍可能在 Leader 恢复时发送。

要求：区分明确发送失败的可编辑草稿、提交结果未知需对账的请求、已经接受消息的普通成员补传。不能盲目自动发表失败草稿；丢 ACK 要先查同 ID 决策并幂等恢复。必要时提供明确取消/重试状态，不能承诺撤回已提交消息。

验收：离线发送失败→修改或移除草稿→Leader 恢复，不自动发旧稿；已接受消息的离线成员补传仍自动执行；回执丢失不重复发表。

### 6. 重要：生产环境孤儿清理与失效上传记录

位置：`lib/room-blob-store.mjs:252`。

collectOrphans 只有测试调用，选择后移除/放弃的上传长期占用配额，宽限期后也不会释放。

要求：接入真实节点生命周期的延迟清理及错误记录；保护已提交 pin、仍有效意图、在途读写，清理一致的失效 upload 记录，不删除未知非本插件文件。不能自动释放已发表引用。与第 5 项一起明确取消/过期状态，避免永久保守 pin 耗尽配额。

验收：真实上传后放弃，超过配置宽限期并执行生产清理路径后释放配额；提交、在途、仍有效重试不受损；重启/写失败可恢复，不误删外来文件。

### 7. 重要：Leader/holder 的按需拉取与迟到成员

位置：`lib/room-attachment-service.mjs:32`、`:73`。

读取只打开本地文件，普通成员补传依赖原发送者推送。原发送者离线、Leader 在线时，迟到成员拿不到所需引用和字节；readPeerBlob 没有生产调用，holder 声明未完成产品接线。

要求：按设计第 103/107 行接入不可变引用与独立可变 holder 信息、授权的元数据/按需拉取路径，校验目标成员和完整字节后再成为 holder。不能用摘要知识或 holder 声明本身授予跨房间读取权。

验收：A 发给 Leader B 后 A 离线；合法迟到成员 C 在 B 在线时能取得被授权的引用并从 B 读取校验后的文件；无可达 holder 时明确不可用，非成员和别的房间拒绝；不需 A 回来。

### 8. 重要：旧普通成员收到可读降级通知

位置：`lib/room-attachment-service.mjs:60`。

目前旧普通节点只有发送端投递失败记录，接收端看不到正文、文件名和附件不可预览说明，遗漏设计第 233 行。此处可读降级不等于禁止的内联字节降级。

要求：旧普通成员收到明确可读的正文/文件名/不支持附件提示，不发送新 base64，不宣称文件已送达。保留精确 mentions 的安全边界，不能降级成意外广播。旧 Leader 仍拒绝附件提交；升级后的补传和稳定 ID 需可解释且不重复正文。

验收：新 sender+新 Leader+旧普通节点真实 HTTP 混合版本；旧端看见可读提示，sender 标明元数据/字节投递差异；旧 Leader 失败保留草稿；不支持精确引用时不得扩大接收目标。

### 9. 次要：同内容多附件的界面 key

位置：`client.js:1292`。

当前卡片 key 只有 blobId；相同字节但不同文件名或重复选择产生重复 key。改为消息内逐项稳定且唯一的标识，存储继续按内容去重。

验收：同字节不同文件名两项独立展示与下载，移除不串位，实际渲染无重复 key 警告。
