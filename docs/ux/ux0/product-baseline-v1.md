## 0. 致 Codex：本轮最重要的交付要求

这不是一句“把 UI 做好看”的开放式提示词。请将本文作为**可追踪的产品需求与验收契约**执行。

1. **先分析当前真实 UI 和代码，交付完整的可视化设计方案，再动业务界面代码。** 至少展示「网络总览、Room 聊天、收件箱」三个页面在桌面宽度下的设计稿，以及窄窗口的关键适配；以实际可打开的静态预览或截图供负责人确认。

3. **复用已实现的 M1～M5 能力。** 不创建第二套 Mesh、Room、附件、文档、任务执行或审批状态机。

5. 当前只要求 UX 设计与增量实施规划；与协议、安全模型、执行调度或自动合并有关的功能必须单独评审。GitHub 推送继续暂停，除非负责人重新授权。

## 1. 产品定位与成功标准

**产品定位**：DSH 客户端中的「局域网 Agent 协作工作台」，不是普通群聊，也不是单纯的设备监控工具。

用户应能在同一个入口回答五个问题：

- **谁在线**：有哪些电脑、DSH 实例和 Agent？连接是否健康？
- **在哪里协作**：我有哪些项目/Room？哪些消息需要处理？
- **正在做什么**：哪个 Agent 在执行什么任务？是否需要人工确认？
- **交付了什么**：文件、文档修订和任务成果在哪里？是否已通过验收？
- **出问题怎么办**：连接、权限、传输或执行异常如何定位？

成功不是增加视觉特效，而是**减少寻找入口、辨认状态、定位失败和完成任务所需的操作**。

### 1.1 不可改变的五项架构决策

| 编号 | 冻结决策 | UX 含义 |
|---|---|---|
| ADR-001 | P2P + 每 Team 固定 Leader | 明确显示 Leader，不提供自动选主的假交互 |
| ADR-002 | Worker 独立目录/Git Worktree | 成果面板展示 Repo、Branch、Commit/Artifact，不声称跨机路径可直接访问 |
| ADR-003 | 计划先人工批准后执行 | 草稿、待审批和可执行必须视觉上区分；审批绑定版本 |
| ADR-004 | Leader 故障暂停 + 人工接管 | 显示暂停/待核对，不能自动恢复调度 |
| ADR-005 | 成果审查 + 人工确认合并 | Worker 完成不等于 accepted；不能显示“已自动合并” |

### 1.2 已有功能基线（须由 Codex 再以实际 checkout 核实）

- M1：Team 执行账本、ACK、租约、结果核对；真实三机验收未完成。
- M2：精确 `@Agent`、机器身份、Skill 引用和 Room Composer。
- M3：附件存储、跨节点传输、授权、校验、重试等已开发。
- M4：共享 Markdown、固定修订、冲突和历史。
- M5：固定版本 Context、投递与审计。
- G1：静态 Peer、离线依赖安装、只读诊断已做一定程度的软件验证。
- G2：`@文档` 已在本地 0.4.4 交付；任务结果固定引用 0.4.5 仍在进行。
- M6：计划审批、自动 DAG 调度尚未正式作为稳定功能交付。

## 4. 信息架构：从“长侧栏 + 大页面”到工作区

### 4.1 一级导航（稳定）

1. **网络**：拓扑、节点列表、连接、健康。
2. **协作**：项目/Room、聊天、文档、附件、收件箱。
3. **任务**：Team、计划、任务、执行、Review（依照已交付能力渐进开放）。
4. **管理**：本机身份、可信节点、诊断、设置（不与日常项目混排）。

左侧推荐结构：

- 顶部：`LAN Mesh` 标题、总连接状态、可展开的本机标识；版本号放到关于/状态详情，不挤在标题行。
- 第一组：网络总览、收件箱（未读数）、任务（待办数）。
- 第二组：我的项目，可折叠项目树、搜索/创建；每个项目只出现一次，行尾 `…` 显示设置、归档等操作。
- 第三组：发现项目，显示数量与按钮，点击进入面板/抽屉；不要把多个“加入”卡片长驻在侧栏。
- 底部：节点健康和设置入口。

**宽度建议**：展开侧栏 260–288px，最大不超过 320px；可折叠为 64–72px 图标栏。不可因为导航标题过长而出现不规则换行。此处为设计建议，最终以设计稿验证。

### 4.2 全局布局

- 工作区标题栏：名称、重要上下文（项目/设备、在线状态）、关键操作。统一高度约 56px。
- 主要内容区：根据页面使用列表/对话/图形，不强制所有页面占满宽度。
- 可选详情侧栏：节点详情、消息详情、Task/Execution 详情，桌面端约 300–380px；窄窗口改为抽屉。
- 全局状态：Loading、Empty、Permission Denied、Disconnected、Stale、Error 必须有确定的语义与恢复入口。
- 深色/浅色主题跟随 DSH 官方主题变量；不能自行硬编码一套与宿主冲突的全局 CSS。

## 5. 页面设计规格

### 5.1 网络总览（UX-4，先设计，后开发）

**用途**：让用户在 5 秒内知道哪些设备连上、Agent 在哪里、谁可以接任务。

**主要区块**：

- 顶部状态摘要：节点总数、已连接、可唤醒 Agent、异常（按真实数据计算；无数据不显示假数字）。
- 主视图切换：**拓扑 / 列表**。拓扑默认以本机为中心，Peer 通过边相连。列表是平等且完整的操作入口，防止 30 个节点时拓扑不可用。
- 节点卡：机器显示名、唯一标识缩写、Agent 数、连接方式、最近活动时间、状态。避免暴露完整公网地址，敏感 IP 默认遮蔽。
- 点开设备：展示实例/会话、能力、允许操作、连接错误和可用的安全操作。相同名称 Agent 显示机器消歧。
- 连接线状态：只使用**真实可观测**链路信息，不推断不存在的公网/隧道类型。离线/不确定要区分。
- 可用操作：刷新/重新探测/复制已脱敏诊断；配对、撤销等若后端未实现则不显示可执行按钮。

**可用性**：支持 1、3、10、30 个 Peer；缩放/布局后能定位节点；窄屏切换列表；支持键盘选择与详情。性能和状态刷新必须可控。

### 5.2 协作 Room（UX-2）

**顶部**：房间名、成员数/设备数、连接状态和 `…` 操作；标签页 `对话 | 文档 | 任务 | 成员`，其中“任务”必须尊重 M6 门槛，不强行打开尚未实现的自动调度。

**消息**：

- 对话阅读区建议最大宽度 860–960px，在宽屏居中；不能把每个气泡铺成近全屏宽。
- 作者身份：头像或图标、显示名、`机器名称`、角色/人类或 Agent；同名成员可通过机器名区分。
- 连续短时间同作者消息合并视觉分组；悬停/展开可见准确时间。保留真实完整时间的查看入口。
- 人类、Agent、系统事件、任务事件四类消息有独立视觉语义；颜色不能是唯一差异，避免全屏绿色气泡。
- 长文字默认显示合理长度并提供展开；代码、错误、引用、文件、文档修订分块显示；全文可复制。
- 历史滚动时不因新消息强制跳到最底；若用户不在底部显示“有新消息”跳转按钮。

**Composer**：

- 与对话阅读列宽度一致，底部固定，不覆盖最后一条消息。
- 保留文字发送、@ Agent/机器、@文档固定修订、Skill 引用、附件/图片和设为任务等已有能力。
- 引用对象在发送前清楚显示，能够移除；异步加载、失败和跨房间切换要保护草稿。
- 不直接把官方 Session Composer 移植成 Room 发送管线；继续走现有 Room 协议。
- 发送、上传、阅读权限拒绝均有可理解错误文案，失败不清空草稿。

### 5.3 收件箱（UX-3）

- 标题显示未读数、过滤条件和“全部标为已读”，批量操作需防误触。
- 顶部过滤：全部/未读/@我/任务/系统；只在现有数据具备区分信息时启用；搜索可按项目和正文。
- 主列表以行式展示，单条摘要最多两行：`图标/来源 → 标题/摘要 → 项目 → 时间/未读状态`。
- 默认按时间倒序，按项目/日期或同一任务聚合可以渐进增强，但不丢失单条消息。
- 点击列表在侧边详情中展开完整内容、关联 Room/Task，并给出“前往来源”的直接入口。
- 26 条及更多消息无需通过滚动巨大卡片完成浏览；长内容保持可检索但不默认铺开。
- 未读数、全部已读操作与后台数据同步；显示失败/重试，不通过 UI 乐观状态隐瞒写入失败。

### 5.4 任务与 Agent Team（UX-5；需等 M6 实际门槛）

- `计划`、`执行中`、`待审查`、`已完成`、`异常/需接管` 使用明确栏目/筛选；任务编号、负责人、依赖和当前尝试可见。
- Task 和 Execution 单独展示：Task 的验收状态不由 Worker 的“完成”自动决定。
- 任务详情可查看依赖、上下文版本、Worker、日志、Artifact、测试证据及人工审查记录。
- 计划草稿、版本差异、批准范围与批准人应可理解；未审批计划禁止派发。
- Leader 断线或执行 `uncertain` 时展示冻结/待人工核对，不提供“安全自动重试”的假按钮。
- 仅在 M6 实际实现后显示可操作 DAG 与审批；此前可显示只读已有执行台账和设计占位说明。
- “合并”必须是独立、真实权限控制的人工动作，不能仅在前端用确认框模拟授权。

### 5.5 文件、文档与诊断（按已有数据复用）

- **文件**：跨机传输记录、来源、目标、大小、状态、哈希校验、失败与重试入口；现有 Artifact 权威系统唯一数据来源。
- **文档**：目录、修订号、提交者、最近修改、引用到任务/消息的固定版本；冲突与提案历史清晰展示。
- **诊断**：节点发现、静态 Peer、签名/信任、宿主可用性、文件传输、任务执行分不同维度检查；从当前已有只读诊断脚本映射到用户可见报告。禁止在诊断结果中泄露密钥或真实敏感路径。
- **配对与 ACL**：单独能力评审，第一批只显示现有可信状态；不因 UI 需要而擅自新增可远程 Shell 或控制系统的权限。

## 6. 视觉语言与交互规范

### 6.1 总体风格

关键词：**专业、安静、清晰、紧凑但不拥挤、与 DSH 官方一致**。尽量使用现有主题变量、字体、边框、按钮和图标。避免大面积荧光色、粗黑描边、滥用阴影、渐变和闪烁状态。

| 属性 | 设计约束 |
|---|---|
| 颜色 | 语义色：连接正常、警告、危险、执行、待审批；浅色/深色均需可辨 |
| 排版 | 统一 12/14/16/20px 等级，标题/说明/元数据/正文有固定层级 |
| 间距 | 采用 4/8/12/16/24 的间距序列，卡片内外留白一致 |
| 圆角 | 按组件层级使用 6/10/14px 等有限档位，不遍地胶囊 |
| 线框 | 浅色细分隔、重点用强调线和内容层次；不使用每条列表一圈粗黑边 |
| 图标 | 优先宿主已有图标系统，图标均配可访问标签 |
| 动效 | 只对展开、选中、加载、状态变更使用轻量动画；遵守减少动态效果偏好 |
| 信息密度 | Inbox 紧凑、Room 阅读舒适、诊断高密度、DAG 可缩放，不统一一个密度 |

### 6.2 响应式与可访问性

- 至少审查：桌面 `1920×1080`、`1440×900`、`1280×720`；窄窗口 `1024×768`。如果支持移动视图，增加 `390×844`。
- 侧栏可折叠；窄窗口详情面板转抽屉；Composer 及操作按钮不能被遮挡。
- Tab 顺序合理，Enter/Escape 行为一致；菜单有焦点管理，键盘可完成常见操作。
- 不依赖颜色传达在线/失败；状态有文字及图标。文本对比度按 WCAG AA 目标检查。
- 支持超长机器名、重复 Agent 名、中文/英文混排、空项目、断线、异步刷新。

## 7. 数据映射与工程边界

先建立「现有后端返回值 → UI ViewModel」映射清单，禁止凭空添加假字段。以下仅为**视图概念**，不是要求修改协议：

| ViewModel | 数据来源核查方向 | 禁止误用 |
|---|---|---|
| NodeView | 发现/静态 Peer/连接状态 | 节点在线 ≠ Agent 可执行 |
| AgentView | session 与宿主状态 | 名称非唯一，需机器/Session 消歧 |
| RoomView | Room 状态/成员/生命周期 | 客户端列表 ≠ Room 最终写入权威 |
| InboxView | 提醒及未读存储 | UI 已读 ≠ 服务端提交成功 |
| MessageView | Room 消息及引用 | 文档引用不等于 @Agent 唤醒 |
| ArtifactView | M3 文件记录 | 远程绝对路径不等于已传输文件 |
| TeamTaskView | M1 Team Task | Execution succeeded ≠ Task accepted |
| DiagnosticView | 只读检查报告 | 未检查项目显示 unknown，不显示绿色通过 |

技术要求：

1. 不改变 `lib/transport.mjs`、Team 执行状态机、Room 消息语义来适应新 UI；若必须扩展接口，先提出数据契约和兼容方案，获得审批。
2. UI 重构以**小组件拆分和 ViewModel 转换**为主，不把新的全局状态或副作用塞进 `client.js` 无限制增长。
3. 新 UI 必须读取已有真实数据；可在设计预览使用明确标注的假数据，但交付生产界面不得保留伪状态。
4. 当前任务成果引用 0.4.5 及 M6 草稿须独立保护。UI 分支从负责人确认的干净基线创建，避免误合入进行中的业务代码。
5. 不擅自推送 GitHub、改许可证、修改用户配置、删除 Room/Task/文档历史或修改数据库结构。

## 9. 验收矩阵（最低要求）

| ID | 场景 | 判定标准 |
|---|---|---|
| UX-A01 | 1440×900，侧栏展开与折叠 | 标题不异常换行，常用入口清晰，功能均能到达 |
| UX-A02 | 1280×720、1024×768 | 无横向溢出，聊天输入框/主要按钮不被遮挡 |
| UX-A03 | 26 条 Inbox，3 个项目，含超长消息 | 列表摘要最多两行，可进入全文；未读数字准确 |
| UX-A04 | Inbox 标记已读成功/失败 | 数据与 UI 最终一致；失败有可重试反馈 |
| UX-A05 | 2 台机器各有同名 Agent | 消息和候选明确显示机器；精确路由不退化 |
| UX-A06 | Room 连续 5 条同作者消息、1 条超长代码 | 发送者分组正确，文本可展开复制，滚动稳定 |
| UX-A07 | Room 发送：文本、@Agent、@文档、Skill 引用 | 协议和结果与改版前一致，不误触发 Skill/错误 Agent |
| UX-A08 | 图片拖拽/粘贴、多附件失败/重试 | 上传进度与失败清晰，失败保留草稿，不重复消息 |
| UX-A09 | 旧 Room、归档 Room、文档固定修订 | 可访问状态正确，归档只读不被 UI 绕过 |
| UX-A10 | 节点 1/3/10/30，含重名/离线/unknown | 拓扑与列表一致，状态语义真实，详情可访问 |
| UX-A11 | Leader 离线 / Task uncertain | 不显示成功或安全自动重试；任务停止自动推进 |
| UX-A12 | 计划未批准 / Review 未通过 | UI 不提供越权派发或合并入口；权限由后端二次验证 |
| UX-A13 | 深/浅主题与键盘操作 | 对比度、焦点可见、菜单可用，颜色不是唯一状态依据 |
| UX-A14 | DSH 版本兼容与 UI 回归 | `panel-check`、Schema、Composer 兼容检查无退化，记录真实数量 |
| UX-A15 | 断网后重新连接/页面重载 | 状态解释正确，已保存消息/文档/设置没有丢失 |

自动测试只能覆盖可自动化部分；至少需要一次真实浏览器目测和两节点操作验证。凡未执行的用例标记 `NOT RUN`，不得记为通过。改版前后截图必须来自同一分辨率和同类数据，避免人为制造视觉对比。

## 10. 每批开发流程与停止条件

1. **Before**：记录分支、SHA、工作区状态；保留 0.4.5/M6 草稿；确认本批可改文件。
2. **Design**：提交方案、线框/高保真效果、交互状态表；与负责人确认。
3. **Implement**：一次只改一个 UI 批次；避免顺手改后端、安全、协议。
4. **Verify**：单元/面板/Schema/Composer 检查，浏览器截图与手工流程核对。失败不掩盖。
5. **Review**：Codex 对真实 Diff、组件职责、协议影响、安全性和视觉效果独立复核。
6. **Handoff**：按 `完成能力 / 截图 / 测试 / 未完成 / 风险 / 下一批建议` 输出。

停止并请求批准的情形：需要重做现有协议；需要迁移数据；新增远程系统控制或改变可信模型；实现自动选主/自动合并；破坏未完工工作树；无法保证旧 Room/Team 行为；重要设计与已冻结 ADR 冲突。
