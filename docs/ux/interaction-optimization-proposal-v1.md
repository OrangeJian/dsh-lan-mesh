## 二、背景与目标

### 2.1 背景

面板已历经 0.4.6—0.4.38 多轮 UX 迭代，具备两栏工作区、四页签房间、网络拓扑、任务看板等完整结构，工程与可访问性基础扎实。**但当前优化重心偏"组件几何与回归证据"，真实高频使用中的认知负担尚未系统处理**：本轮走查在一个真实使用过的房间里，观察到消息刷屏、误导性文案、同名项目无法区分、内部术语外露等直接影响"看懂与操作"的问题。

### 2.2 要解决的问题

1. **读不动**：聊天流中大量重复短回复淹没有效信息，长历史定位困难。
2. **看不懂**：内部状态词（未核对/未知）、裸 id、误导性文案直接暴露给用户。
3. **分不清**：同名房间/会话在列表中几乎无差异，消歧责任被甩给用户。
4. **反馈弱**：错误被兜底成单一提示，用户无法判断"是我的问题还是系统问题、下一步做什么"。

### 2.3 成功指标与口径

> 口径：以下为**建议目标值（估算）**，需在 V1.1 上线前后用同一房间样本对比确认；"基线"指本轮走查的实测观察，非埋点实测值。

| 指标 | 定义与口径 | 基线（本轮观察） | 目标（V1.1） |
|---|---|---|---|
| 重复消息折叠率 | 连续同作者、语义高度相似的短回复被折叠的比例 | 0%（未折叠） | ≥90% |
| 房间列表消歧可辨率 | 同名项目在卡片层可被用户区分（有差异标识）的比例 | 0/2（两个 Bridge Build 无法区分） | 100% |
| 误导文案数量 | 显示内容与实际选项/状态不符的文案条数 | ≥2（成员下拉、网络未核对） | 0 |
| 错误可操作性 | 错误提示包含"原因+下一步动作"的比例 | 0（单一兜底码） | 100% |

## 四、优化原则

1. **降噪优先于加功能**：先删/藏无效信息（裸 id、重复回复、常驻按钮），再加引导，避免界面更复杂。
2. **消歧责任在系统，不在用户**：同名/相似对象必须由界面给出差异标识，不能只写一句"请自行核对"。
3. **用户语言替代内部术语**：状态词面向"人"解释；技术细节收进 hover / 诊断折叠区。
4. **反馈可执行**：每条错误给出"发生了什么 + 你能做什么"。
5. **不改权限模型、不碰后端业务语义**：本方案为表现层与错误映射优化；涉及服务端字段/契约的项单列依赖（第九节）。
6. **保持工程底线**：沿用现有设计 token、深浅主题、容器查询与可访问性；遵守 `npm run build:client` 同步源码与产物的开发约束（见第九节）。

## 六、功能需求详述

> 状态词约定：**必须**（shall，强制）/ **应该**（should，建议）/ **可以**（may，可选）/ **禁止**（must not，强制不）。每条含：问题 → 方案 → 线框/交互 → 验收标准（Given/When/Then）→ 代码落点（需实现前核对）。

### FR-01 连续重复消息折叠（P0）

**问题**：P-01。真实房间中 agent 连续发出多条语义相近的短回复，逐条全展开占用大量纵向空间。

**方案**：
- 对**同一发送者**、在时间窗（建议 5 分钟，可配置）内、正文归一化后高度相似的连续短消息（建议 ≤120 字），默认折叠为一条摘要行："`{作者}` 的 N 条相似回复"，点击展开全部。
- 归一化规则：去除标点/空白差异、去除末尾"不再回复/无待办"等口头禅；相似度判定用轻量规则或本地算法，**不调用模型**。
- 折叠必须可逆：展开后每条消息保持原文、时间、复制能力；刷新后折叠状态可重算。
- 禁止折叠不同作者的消息；禁止把折叠后的内容永久丢弃。

**线框/交互**：
```
┌────────────────────────────────────────┐
│ 现在我们需要做一个自动化任 · Agent        │
│ ▸ 连续 4 条相似回复        13:03:01–13:03:26 │  ← 折叠态（默认）
└────────────────────────────────────────┘
点击 ▸ 展开：
┌────────────────────────────────────────┐
│ ▾ 连续 4 条相似回复                       │
│   ├ 收到。时间线…不再回复。      13:03:01  │
│   ├ 收到。这条线到此为止…        13:03:14  │
│   └ …（每条仍可复制全文）                 │
└────────────────────────────────────────┘
```

**验收标准**：
- Given 房间内有 4 条同作者、5 分钟内、正文高度相似的短消息，When 打开对话页，Then 默认显示 1 条折叠摘要行，正文不逐条展开。
- Given 折叠态，When 点击摘要行，Then 展开全部 4 条原文，每条时间与复制按钮可用。
- Given 4 条消息中混入 1 条不同作者或间隔 >5 分钟，When 渲染，Then 不得将其并入同一折叠组。
- Given 长正文（>120 字）或含代码块的相似消息，When 渲染，Then 不折叠，保持原样。

**代码落点（实现前核对）**：`ui/models/room-message-model.mjs`（消息投影/分组）、`ui/models/room-timeline.mjs`、`ui/room/message-body.mjs`、`ui/room/message-timeline.css`；构建产物 `client.js`。

### FR-02 成员邀请下拉文案与选项修正（P0）

**问题**：P-04。默认文案"本节点没有可拉进来的会话"与实际 28 个可选自相矛盾；选项显示原始 id。

**方案**：
- 下拉默认文案必须按真实情况生成：有可邀请会话时显示"选择要拉进来的会话（N）"；确实为空时才显示"本节点没有可拉进来的会话"。
- 候选列表**必须过滤已在房内的会话**，并显示会话标题（`title → name → shortId` 逐级兜底），禁止只显示"会话 999c2dde"原始终端 id；原始 id 收进 hover `title`。
- "拉进来"按钮在无有效选择时 disabled 且给出原因（见 FR-11 复用禁用态说明）。

**验收标准**：
- Given 本机有 28 个会话、其中当前会话已在房内，When 打开成员页，Then 默认文案显示可邀请数量，下拉不列出已入房会话，选项显示会话标题。
- Given 本机确无可邀请会话，When 打开成员页，Then 才显示"本节点没有可拉进来的会话"且"拉进来"按钮禁用。
- Given 两个会话标题相同，When 展示候选，Then 重名项追加短 id 区分，与 `@` 提及的消歧规则一致。
- Given 无权限成员查看成员页，When 渲染，Then 不展示邀请下拉与按钮（沿用现有 leader 权限）。

**代码落点（实现前核对）**：房间成员页签组件（`client.js` 内联 / `ui/models/workbench-identity.mjs` 需核对）、候选投影 `ui/models/*`；契约见 `docs/ui-contract.md` §4。

### FR-03 发现项目同名消歧与信息净化（P0）

**问题**：P-05/P-06。两个"Bridge Build"卡片几乎相同；"负责人未知·设备未知"无价值；room id 裸奔；消歧责任靠顶部文案甩给用户。

**方案**：
- 同名/相似项目卡片**必须**在卡片层给出至少 2 个可辨差异标识：房间短 id（如 `#3805b8f7`）、描述、来源设备/节点（有则显示）。差异字段要视觉突出，相同字段弱化。
- 当 leader/设备未知时，**禁止**显示"负责人未知 · 设备未知"这类空值占位；改为显示对决策有用的信息（成员数、最近活跃时间——若后端可得；不可得则显示 room 短 id）。
- room id 默认折叠为短码，完整 id 收进 hover 或"详情"；禁止整串裸显示。
- 加入动作前增加**轻量二次确认**：弹层显示项目名 + 短 id + 描述 + 来源，用户确认后执行 `roomJoin`（防误加同名项目）。
- 顶部"请自行核对"文案改为系统已做消歧后的引导："同名项目已按房间编号区分，加入前请确认目标"。

**验收标准**：
- Given 发现列表有 2 个同名"Bridge Build"，When 展示卡片，Then 每张卡片有可辨的房间短 id 标识，两张卡片视觉上可区分。
- Given 项目 leader/设备未知，When 渲染卡片，Then 不出现"负责人未知/设备未知"占位文案。
- Given 任意项目卡片，When 渲染，Then 完整 room id 不以整串可见文本呈现（hover/详情可见）。
- Given 用户点击"加入"，When 弹出确认层，Then 显示可辨识的项目信息；取消不产生加入；确认才调用 `roomJoin`。
- Given 同名项目，When 加入，Then 请求携带精确 room id，不按名字操作。

**代码落点（实现前核对）**：发现项目浮层组件（`client.js` 内联 / `ui/shell/*` 需核对）、项目投影 `ui/models/project-navigation.mjs`；房间身份规则见 `docs/ui-contract.md`。

### FR-04 错误码细分与可操作反馈（P0）

**问题**：P-08。多个语义不同的错误被兜底成 `LAN_MESH_FAILED`，用户无法判断责任与下一步。

**方案**：
- 面板错误映射**必须**为下列语义各给出独立用户提示（原因 + 下一步动作），禁止统一兜底：
  - `FORBIDDEN` / 非成员 → "你不是这个房间的成员，请让房主拉你入房"；
  - `NOT_READY` / 服务未就绪 → "协作服务尚未就绪，请稍后重试或刷新"；
  - `TEAM_DISABLED` → "该房间的团队执行未开启"；
  - `TEAM_STORAGE` → "本地存储异常，请检查磁盘空间或联系管理员"；
  - `STALE_GENERATION` / `APPROVAL_BINDING_MISMATCH` → "数据已更新，请刷新后重试"。
- 未知错误保留通用兜底，但必须带"可复制的错误码"以便反馈。
- 涉及 Team 只读投影时，字段层用 `known` + `teamStatus:'absent'` + `taskCounts:null` 区分"无数据/未就绪/真的 0 个任务"，禁止抹平成健康态（沿用 `ux6-matrix-report.md` §5 的硬发现）。

**验收标准**：
- Given 服务端返回 `FORBIDDEN`，When 面板展示错误，Then 显示"你不是这个房间的成员…"且不出现 `LAN_MESH_FAILED`。
- Given 返回 `TEAM_STORAGE` 与 `NOT_READY`，When 展示，Then 两条提示文案不同且各含下一步动作。
- Given 一个未登记的新错误码，When 展示，Then 显示通用提示并提供可复制的原始错误码。
- Given Team 数据 absent，When 展示看板，Then 呈现"未就绪/无数据"态而非 0 或绿色健康态。

**代码落点（实现前核对）**：`index.js` 错误码映射（文档定位约 1592–1604 行）、面板错误展示组件；契约见 `docs/ux/ux6-matrix-report.md` §5、`docs/ux/team-owner-readonly-contract.md`。

### FR-05 消息元信息降噪（P1）

**问题**：P-03。每条消息常驻"复制全文"；作者行平铺设备名/node id/时间。

**方案**：
- "复制全文"由常驻改为**按需出现**：hover 消息或键盘聚焦时显示；触屏/无 hover 环境保留一个轻量"更多"入口。
- 作者行只保留：显示名（加粗）+ 相对/绝对时间；设备名、node id 收进 hover `title` 或"消息详情"。
- 已按发送者分组的连续消息，同组内后续消息可省略重复身份行（沿用 UX-2a 分组能力），只保留时间。
- 必须保证复制、来源追溯能力不丢失（可访问性：键盘可达、读屏可读）。

**验收标准**：
- Given 一条消息，When 鼠标未 hover 且未聚焦，Then "复制全文"不作为常驻按钮占据版面。
- Given hover 或键盘聚焦该消息，When 交互，Then 复制入口可达且点击可复制原文。
- Given 消息含设备名/node id，When 默认渲染，Then 不在作者行以可见正文平铺（可在 hover title 中）。
- Given 读屏用户，When 浏览消息，Then 作者与时间仍可被朗读。

**代码落点（实现前核对）**：`ui/room/message-body.mjs`、`ui/models/room-message-model.mjs`、`ui/room/message-timeline.css`。

### FR-06 网络术语用户化与单机空态引导（P1）

**问题**：P-07。内部状态词外露；单机时空拓扑无引导。

**方案**：
- 将"派发权限未核对""本机执行状态未知""来源 本机记录"等改为用户语言，并在旁边提供 `?` tooltip 解释口径，例如："派发权限：尚未核对（表示当前未确认是否可对端派活，不代表没有权限）"。
- 拓扑区在"发现节点 0"时显示**引导空态**：一句说明（"当前只发现本机"）+ 可操作建议（"确认对端插件已安装、discoveryPort 一致、同一局域网并放行 UDP 45870/TCP 45871"）+ 一个"重新扫描"入口。
- "未核对"状态必须明确其含义是"未验证"而非"不可用"，避免误判为故障。

**验收标准**：
- Given 网络总览任一"未核对/未知"标签，When hover `?`，Then 显示口径解释，且不把它表述为"不可用"。
- Given 发现节点 0，When 渲染拓扑区，Then 显示引导空态与排查建议，而非仅一个孤立节点 + 大面积留白。
- Given 有对端节点，When 渲染，Then 正常显示拓扑/列表切换，不受空态引导影响。

**代码落点（实现前核对）**：`ui/network/network-workbench.mjs`、`ui/network/network-workbench.css`；生成取证 `scripts/network-workbench-preview.mjs` 需同步补空态 fixture。

### FR-07 补齐 offline 视觉状态（P1）

**问题**：P-11（已知缺口）。Network 组件只有 local/stale，无 offline/disabled 类，导致"设备离线"判据（A10/A11）无法呈现与验收。

**方案**：
- 在 Network 组件增加 `offline`（离线）与可选 `disabled` 语义状态及对应视觉（灰阶/断线图标/文字标签），与 `stale`（数据陈旧）明确区分。
- 状态语义必须可读：offline = 已知失联；stale = 有数据但未核对。二者不得混用。
- 补生成器 fixture（`scripts/network-workbench-preview.mjs`）覆盖 offline 态，纳入回归。

**验收标准**：
- Given 一个被判定为离线的节点，When 渲染，Then 显示 offline 专属视觉标签，与 stale 明显不同。
- Given 生成器跑 offline fixture，When 校验，Then 无横向溢出、状态标签可见、判据 A10 的"离线"子项有证据形态。
- Given 断网重连，When 状态恢复，Then offline 态正确撤销（沿用现有轮询/发现机制，不新增长连接）。

**代码落点（实现前核对）**：`ui/network/network-workbench.mjs`（当前 `mode = nodes.length>10 ? 'list' : 'topology'`）、`ui/network/network-workbench.css`、生成器与 `docs/ux/network-workbench-preview/`。

### FR-08 长历史定位与"回到最新"（P1）

**问题**：P-02。长历史中顶部消息被裁切，缺"回到最新"入口。

**方案**：
- 对话区首次进入/real-time 场景沿用"接近底部跟随最新"，读历史保留锚点（UX-2b 已有能力，回归保护，不重做）。
- 当用户向上滚动离开底部超过阈值（建议 1 屏），显示悬浮"回到最新（N 条新消息）"按钮，点击平滑滚动到底部并清零计数。
- 新消息到达时若用户正在读历史，不强制滚动，累加未读计数；仅在用户主动点按钮或本就在底部时跟随。

**验收标准**：
- Given 用户在读历史且离底部 >1 屏，When 新消息到达，Then 不强制跳转，显示"回到最新（N）"。
- Given 点击"回到最新"，When 滚动完成，Then 停在最新消息、计数清零。
- Given 用户本就在底部，When 新消息到达，Then 自动跟随（保持现有行为）。

**代码落点（实现前核对）**：`ui/models/room-timeline.mjs`、`ui/room/message-timeline.css`、历史分页 `docs/ux/history-pagination-report.md` 相关组件。

### FR-09 全局导航去重（P2，待决策）

**问题**：P-09。主区顶部"切换工作区或项目"下拉与左侧栏导航职责重叠。

**方案（备选，需决策后实施）**：
- 方案 A（推荐）：保留左栏为主导航，主区顶部下拉降级为"当前位置"面包屑（只读展示 + 点击展开快速跳转），弱化其"第二套导航"心智。
- 方案 B：移除顶部下拉，跳转统一收敛到左栏；风险是用户在房间内需回左栏切换，路径变长。
- 必须先做需求侧定性（顶部下拉的真实使用率），再选 A/B；禁止两个方案同时上。

**验收标准**：
- Given 决策选定方案 A，When 进入任一页面，Then 顶部显示当前位置且左栏仍为唯一主导航入口。
- Given 方案 B，When 移除顶部下拉，Then 所有原可跳转目标在左栏均有等价入口，无功能丢失。

**代码落点（实现前核对）**：`ui/shell/workbench-navigation.mjs`、`ui/shell/workbench-header.mjs`、`ui/models/workspace-navigation.mjs`。

### FR-10 房间草稿轻量保护（P2，待决策）

**问题**：P-11。草稿仅存页面内存，整页/插件重载丢失（项目已明确记录）。

**方案（备选，需决策后实施）**：
- 在现有内存草稿基础上，增加 `sessionStorage` 级别的轻量保存（按 node/session/room 隔离），页面重载后恢复正文与引用；**禁止**写入 `localStorage` 或持久化附件二进制（项目约束）。
- 必须保留现有"导航离开仍卸载 Room、后台确认只消费匹配快照、失败重试保持消息 ID"等语义，不因持久化产生脏回执。
- 附件：重载后提示"附件需重新添加"，不承诺恢复二进制。

**验收标准**：
- Given 用户在房间输入草稿后整页刷新，When 重进同一房间，Then 正文与引用恢复，附件给出需重加提示。
- Given 不同 node/session/room，When 各自编辑，Then 草稿互不串写。
- Given 后台成功回执到达，When 草稿已被用户新编辑覆盖，Then 不误清新草稿（沿用现有快照匹配）。

**代码落点（实现前核对）**：草稿组件 `ui/models/room-composer-drafts.mjs`、`docs/ux/ux1e-drafts-*`；契约 `docs/ui-contract.md` §2026-11-15 UX-1。

### FR-11 禁用态原因说明（P2，随主项顺手做）

**问题**：P-10。"设为任务"等按钮 disabled 但无原因。

**方案**：disabled 按钮必须有可访问的原因说明（`title` + `aria-describedby`），如"只有房间 leader 可以派活""请先选择要拉进来的会话""上传中无法发送"。复用组件统一实现，避免每处各写。

**验收标准**：
- Given 任一禁用按钮，When hover 或聚焦，Then 显示禁用原因，读屏可朗读。
- Given 权限不足导致的禁用，When 说明文案，Then 明确"为什么"和"谁能做"。

**代码落点（实现前核对）**：面板按钮基础组件 / `client.js` 内联。
